# Token Saver

## 项目定位

Token Saver 是一个 Codex 工作流 Skill，用于把工程任务拆成两个清晰的职责：当前对话中被选中的主模型负责理解需求、检查仓库、设计方案、决定风险并审查结果；`gpt-5.6-luna` 在得到明确边界的任务包后负责实现。主模型在必要时接管未完成的部分。

它是工作流编排规则，不是新的模型、代理平台或权限授予工具。它不能保证当前账户或运行环境一定有权使用 Luna 模型。

## 为什么叫 Token Saver

许多工程任务同时需要高质量的上下文判断和重复性的文件实现。Token Saver 让当前主模型保留高价值的需求、架构、风险和验收上下文，并把边界清晰的实现包交给专门的执行模型，从而减少重复解释和不必要的主线程编辑；如果执行模型不可用或结果不合格，主模型仍负责把任务完成。

“Saver”描述的是一种受验收约束的工作流取舍，不是对 token 消耗、速度、质量或成本的承诺。

## 核心工作流

1. 主模型检查相关仓库、用户现有改动和任务要求，并记录可写范围的基线。
2. 主模型解决常规歧义，确定架构、接口、风险、验收标准和实现计划。
3. 主模型读取 [Luna 任务包规范](references/luna-task-packet.md)，为实现工作建立一个自包含的、有明确可写范围的任务包。
4. 在实现阶段，按任务包启动 `gpt-5.6-luna`，目标执行档位为 `high`，并使用 `fork_turns: "none"`，以确保显式模型选择生效。
5. 主模型等待执行结果，重新检查文件、差异、目录和验证输出；不把执行模型的自述当作验收证据。
6. 若结果接近但有明确缺陷，主模型最多发送一个聚焦的、基于证据的修正任务包。
7. 若 Luna 不可用、无法完成或修正后仍未通过，主模型根据接管规则实现未完成部分，并对集成结果做最终验证。

默认使用一个有界实现任务包；只有当文件所有权互不重叠且结果可以分别验证时，才适合拆成多个任务包。每个可写文件只能由一个活动中的执行者负责，主模型负责集成和最终接受。

完整的分层、时序、状态和差异基线策略见 [架构说明](docs/architecture.md)。

## 主模型与 Luna 的职责边界

### 当前主模型

当前对话中实际被选中的模型是控制器，不由本 Skill 替换或硬编码。它负责：

- 仓库检查、需求解释、架构与接口设计；
- 实现计划、风险和安全/授权判断；
- 任务包编写、文件所有权分配和基线记录；
- 结果审查、集成、验证和最终接受；
- 处理需要额外判断的隐私、数据完整性、破坏性迁移、兼容性或安全决策。

主模型不会仅为节省委托开销而直接开始编辑；只有在 Luna 不可用、明确报告不能完成、或修正门禁失败时，才接管未完成的实现。

### `gpt-5.6-luna` / `high`

Luna 的范围是执行已批准的、边界明确的实现包。目标调用配置为：模型 `gpt-5.6-luna`，执行档位 `high`，`fork_turns: "none"`。Luna 不重新定义整体架构，不自行批准安全、隐私、数据完整性或破坏性变更，也不负责最终验收。

Skill 的配置或任务包中出现模型名称，不等于运行时已经证明该模型被调用。只有代理活动或工具结果明确识别为 `gpt-5.6-luna` 时，才可以对外声称 Luna 实际执行过任务。

## 模型不可用、失败与接管规则

以下任一条件成立，即视为 Luna 未能完成当前任务包：

- 模型或内部代理工具不可用；请求被拒绝；或运行时无法确认实际使用的是 `gpt-5.6-luna`；
- Luna 明确报告阻塞，或返回结果缺少要求的实现；
- 新证据要求做任务包之外的架构、安全、隐私、授权、破坏性迁移、数据完整性或破坏兼容性的决定；
- 在授权范围内无法提供必要的验证；
- 初次结果及一次聚焦修正都未通过验收标准。

接管时，主模型应记录具体原因，只重新规划未解决部分，保留已经正确的 Luna 工作，并验证整合后的结果。若显式 Luna 模型被拒绝或不可确认，不得静默换成另一个执行模型。

## 安全与授权边界

- 本 Skill 不授予部署、删除、购买、外部通信、GitHub 操作、推送或其他额外权限。
- 用户最新指令优先；任务包只授权其中列出的文件和操作。未列出的文件、系统或外部服务均不在范围内。
- 不向执行模型发送密钥、令牌、个人资料、私有项目数据或与任务无关的上下文。
- 执行前先做只读检查并记录基线；不使用宽泛的重置、覆盖或破坏性命令来“清理”用户改动。
- 如果发现越界写入、已有用户改动受损或归属无法判断，应停止继续委托，保存证据，由主模型做针对性恢复或请求用户决定。
- 不把截图、Skill 文件、工具提及或模型名称当作外部服务权限、账户资格或业务结果的证明。

这些规则描述的是本地 Codex 工作流边界，并不替代仓库、组织、平台或服务本身的安全策略。

## 安装

从公开仓库取得 `token-saver` 目录后，将整个目录放入 Codex 的 skills 目录，并保留 `SKILL.md`、`references/luna-task-packet.md` 和本 README。例如在 PowerShell 中：

```powershell
$source = "<path-to-repository>\token-saver"
$destination = "$env:CODEX_HOME\skills\token-saver"
Copy-Item -Recurse -Force $source $destination
```

如果环境没有设置 `CODEX_HOME`，请按该 Codex 安装的文档确定 skills 目录后再复制；不要把占位路径直接当作命令执行。安装后重启或重新加载 Codex，使新增 Skill 可用。安装只准备本地 Skill 文件，不会安装模型、改变账户权限或发起网络操作。

## 调用示例

在 Codex 中使用 Skill 名称调用：

```text
$token-saver
请实现这个有界工程任务：为 src/example.py 增加输入校验，并补充对应测试。
要求：只修改 src/example.py 和 tests/test_example.py；先检查现有改动；完成后运行指定测试并报告文件差异。
```

也可以在已有任务中直接说明使用它：

```text
使用 token-saver 处理当前工程任务。先由当前主模型确定方案和验收标准，再将明确的实现包交给 gpt-5.6-luna，目标执行档位为 high；最后检查实际文件和验证结果。
```

示例中的路径、测试和模型可用性只是调用格式示意；实际任务必须以仓库事实、当前运行时能力和用户授权为准。

## 任务包与验证流程

每个实现包应至少明确以下内容：目标、主模型已作出的决定、相关证据、精确可写范围、明确排除项、兼容/安全/隐私约束、验收标准、准确的验证命令，以及期望返回的信息。遇到事实冲突、范围需要实质扩展、需要未经批准的依赖或接口变化、敏感决策，或无法验证时，执行者应停止并返回证据，而不是猜测。

验证分为两道门：

1. **范围与差异门**：对照委托前的状态、差异和文件清单，确认只产生任务包允许的变更，没有破坏用户已有改动。
2. **行为与证据门**：运行与任务风险相称的检查，阅读真实输出，逐条对照验收标准；执行模型的摘要只能作为线索，不能代替检查。

若需要修正，只发送一个聚焦任务包，其中包含失败标准、直接证据、所需修正、可写范围和准确的重跑命令。

## 真实性门禁

Token Saver 强制区分“配置/意图”和“运行时事实”：

- 写入 `gpt-5.6-luna` 的配置，不证明 Luna 已运行；必须有代理活动或工具结果的运行时识别。
- 写入 `high` 的目标执行档位，不证明运行时一定接受了该档位；若不可确认，应如实披露。
- 文件已经生成，不证明实现正确；必须检查最终差异并完成适当验证。
- 验证命令通过，不自动证明未覆盖的行为、部署结果、账户权限或外部服务可用。
- 本 README 不承诺账户一定拥有 Luna 模型权限、固定配额、固定速度或固定质量。
